# Preregistered coverage-protocol pilot

2026-10-24. Question: does an explicit source-unit ledger improve first-pass M1 completion without hiding factual omissions or harming meaning, source attribution, independent reference resolution or cost? This is a diagnostic screening study on new AI-authored fictional answers, not author gold, RAGTruth, a production benchmark or statistical generalization proof. All inference, prompts, cases, request payloads, settings and this plan are frozen before the first model call. The production verifier is not changed.

## Three fixed single-call arms

1. `legacy`: unchanged current DECOMPOSE_PROMPT, original-answer payload and extract_claims validator (exact substrings, occurrence/order, meaningful-character union).
2. `ledger_text`: original answer displayed as lossless ordered source units; output atomic claims plus one explicit ledger entry per unit, including unit_id AND exact source_text echo.
3. `ledger_id`: exactly the same input and shared task/ledger instructions as ledger_text; source_text echo is omitted and code retrieves the unit text by ID.

The direct mechanism comparison is ledger_id versus ledger_text: removing the redundant verbatim echo while retaining identical occurrence IDs, ordering and semantic standards. Legacy versus ledger is an overall representation/protocol comparison: serialization, addressing granularity, claim/source topology and protocol instructions differ. It is not a clean isolated test of IDs or coarser segmentation alone. The general semantic task instructions in both ledger arms are copied verbatim from the existing DECOMPOSE_PROMPT; this parity revision was made before the protocol author read any new case bodies, to avoid mixing in new semantic prompting rules.

Source units split only at fixed punctuation/newline boundaries. They concatenate to the exact original answer, with no normalization, sign/number folding or truncation. IDs identify occurrences, including repeated text. Unit boundaries are not assertions or guaranteed sentence boundaries. A unit can contain multiple facts or factual plus advisory content; a claim may reference multiple units. M1 still controls atomicity. Code only checks IDs/shape and stably orders claim records by first source occurrence; it never changes claim text, merges/deduplicates claims or infers an entity/factual label.

Ledger schema has claims[{claim_id,claim_text}] and coverage[{unit_id,claim_ids,nf_reason}], plus source_text only in ledger_text. Every input unit must appear exactly once in source order. Every claim must be referenced; all references must exist and be unique within an entry. A unit must have nonempty claim_ids or a nonempty model-written nf_reason (or both). Empty/unprocessed units fail; there is no automatic gap-to-NF conversion. A mixed unit is represented by both fields, not excluded wholesale. Claims retain only the actual discrete source_units as provenance; no enclosing span is generated or used as support for intervening text.

This is explicitly a **coarser/different coverage contract**. One referenced claim does not prove all facts within a unit were selected. Tests deliberately accept a syntactically valid ledger with a semantically omitted fact to demonstrate this boundary; semantic review must catch that failure. A 100% structural ledger score cannot be reported as 100% factual recall or equivalent to the legacy validator.

## New materials and execution

20 independent fictional answers across five domains, Chinese/English 10/10. Fifteen factual or mixed answers, with 2–4 target facts each (44 targets total), and five pure-NF answers. Length 92–798 characters; 11 answers have 350–1000 characters, nine of those factual. All fit the unchanged 1200-character single-chunk bound. Despite five domains, many examples are logs, transcriptions or handover instructions; discourse diversity remains limited.

A separate case-author role read task decisions but did not read candidate prompts, prior concrete benchmark cases or prior outputs. A critic reviewed targets before inference. cp005 had an ambiguous batch-versus-kiln pronoun; before inference the author clarified only that antecedent and its exact quoted gold, leaving its four assertions unchanged. Faithful same-sentence repetition is permissible: count the underlying fact once, record duplicate output as redundancy, and do not invent a second event/entity or penalize optional non-merging. None of these AI reviews is author adjudication.

Twenty answers × two repetitions × three arms = **120 provider calls**, one per output. Fixed hash schedule rotates arms so each occupies each position 13 or 14 times; four workers. deepseek-flash, thinking disabled, max output 8192, JSON mode, max_claims 64, upstream_retries 0, repair_attempts 0. No M3, fallback, format retry, second-pass review, best-of selection or model-guided sample selection. Every case is run regardless of previous outcome. Two repetitions do not create forty independent answers. No protocol or score edits after observing outcomes; this set becomes exposed after the run.

All full model requests and hashes are frozen before calls. Runtime receives only answer text plus generated addressing structure, never sample IDs, domain/generator identity, expected targets, labels or scoring metadata. Per-call exclusive fsynced reservation and response files govern accounting; progress.json is only a derived view. Bounded retries apply solely to safe file I/O. A progress-file lock cannot trigger a model retry. Unknown reservations cannot be silently reissued. Full results require an authoritative run-complete seal, 120 unique identities, 120 matching durable reservations/responses and verified frozen inputs. If durability fails, stop new dispatch, retain partial/unknown outcomes and disclose them; there is no automatic resume or resampling.

## Fixed semantic scoring

The primary result is the all-attempt **joint pass**: structurally valid AND all target content retained AND no unasserted claim AND faithful standalone wording/source association/atomicity. Report its numerator /40 per arm and the number of original answers passing in BOTH repetitions /20. This is a research M1 result, not overall /verify accuracy or production completion rate.

Blinded review packets omit arm, prompts, cost, ordering and verbatim echo fields. Normalize claims and actual referenced source fragments so ledger_text and ledger_id cannot be distinguished by the echo field. Legacy source shape may still reveal its representation; this is procedural blinding, not guaranteed concealment. Root and a separate AI reviewer divide outputs, with cross-review of errors/uncertainties. Case labels and semantic judgments are AI drafts, not the user's final adjudication.

For each expected target, record claim indices and:

- `content_retained`: all asserted subject/relation, quantities, sign, polarity, condition, modality, scope and attribution are preserved by the output. A pronoun uniquely resolvable from the original answer/list may retain content while failing the next axis. Ordinary synonymous wording and equivalent numeric rendering are acceptable; do not require a literal target-string match.
- `standalone_retained`: the individual claim supplies its needed antecedent/entity and attribution without relying on another claim. Unresolved Its/it/该室 referring to a named prior entity fails this axis even if content is uniquely recoverable from the answer. Do not demand a fabricated proper name for a genuinely generic subject or one already explicit in that claim. Relations needing multiple facts may be stated in one claim only when they form one independently judgeable assertion; bundling independent assertions fails atomicity.
- `source_supported`: the claim's actual attached source fragments contain its asserted predicate, values, conditions and scope. Multiple unit fragments may jointly support it. Under the EXISTING M1 contract, an explicit shared antecedent may be uniquely resolved from elsewhere in the original answer; do not penalize a correctly expanded subject merely because its name is not repeated inside the attached fragment. This limited antecedent allowance does not permit importing an unrelated predicate, missing condition or factual premise from elsewhere. Whether the antecedent also appears inside the attached fragments is a separate local-source-self-containment diagnostic, not a new main-contract requirement. Exact source text alone does not prove support.

Record every false/changed claim, non-factual item put in claims, unresolved reference, improper compound claim and source mismatch. Faithful redundant claims are a separate diagnostic, not FP. Uncertain interpretation is explicitly flagged with sensitivity bounds; do not decide ambiguities to favor an arm. Do not post-hoc add targets that benefit a preferred arm: record any genuine fixture deficiency and show its effect separately.

Report for each arm:

- Structural completion /40 with detailed failure categories; this cannot substitute for the joint pass.
- Completed target retention /88 (44 targets × two repetitions), plus standalone and provenance retention. Invalid outputs' targets remain technically unserved, not proven semantic omissions.
- Valid-output semantic omissions separately from technical unknown/unserved targets.
- Pure-NF correct AND valid /10, wrong claim-bearing NF answers among valid NF outputs, and NF technical errors separately. Mixed-answer false additions are also reported.
- Selection-only pass (valid + target content + no false addition) separately from strict joint pass, to avoid counting unresolved pronouns as full success.
- Paired changes for ledger_id vs ledger_text and versus legacy, per repeat and per original case. Report new errors, not only net totals; common-valid subsets are diagnostic only.
- Multi-target-unit subset defined before inference: cp001/u0002 (f1,f2), cp005/u0002 (f2,f3), cp017/u0002 (f2,f3). This is THREE original answers, six targets, twelve repeated target opportunities per arm. Check omissions specifically; do not inflate it into many independent examples.

Also review **parseable raw claims** on structurally invalid outputs, solely for a separate diagnostic of content selection. If any claim row is unreadable, mark the full raw extraction unscorable rather than filtering inconvenient rows. Invalid raw output never earns completion or joint-pass credit; source/standalone diagnostics may be unknown if structure prevents reliable interpretation. The paired audit specifically looks for a real raw omission rejected by legacy but accepted structurally by ledger, and for new ledger omissions despite raw legacy retaining the fact. This tests whether changed coverage masks errors. All-cause output metrics and raw diagnostic metrics must remain separate.

## Decision criteria fixed before results

All results and costs will be reported regardless of outcome. For ledger_id to be **worth advancing to an independent broader study**, require all of:

1. Versus legacy, strict joint-pass answers passing both repeats increase by at least two distinct original answers; strict joint-pass output count and structural completion do not decrease. Ledger_id has at most one structural invalid output /40.
2. No decrease in fixed-denominator content, standalone or provenance target retention, no increase in valid semantic omissions or false-claim answers, and no observed new serious condition/negation/attribution/entity damage. The parseable-raw diagnostic must not reveal worse factual selection hidden by relaxed structural checking; unknown raw cases do not count as evidence of non-inferiority.
3. No newly accepted semantically missing-target output relative to a corresponding legacy raw output that retained that target. If two or more independent answers show an accepted ledger omission that legacy rejected, the coarse-coverage masking concern alone rules out advancement. Even one such failure is reported; two is a predeclared screening stop, not a permission to call one safe.
4. At least non-inferior strict joint/target/NF scores versus ledger_text, lower standardized all-cache-miss cost than ledger_text, and total standardized cost at most 1.30× legacy. No max-token truncation.

These are descriptive screening gates, not significance tests or a deployment approval. If completion improves but semantics or cost worsen, report the tradeoff instead of claiming all three improved. If both ledger arms tie structurally, report any cost difference but do not claim an ID-specific completion gain. If factual errors are absent, report observed preservation/ceiling, not improved recall. No automatic production integration follows even if gates pass.
