# 工程机制调研：缩小协议负担，先验证接口能力

调研日期：2026-10-23。范围为当前 context-only、S/C/U、精确引用和有界修复契约；没有更改生产代码、Prompt、模型或评测标签，没有读取新的 RAGTruth 样本文件。本文是定向多源机制研究，不是系统综述，也不是作者裁定。

本次沿用 deep-research 的一手来源核验、反证和“来源发现/本项目猜想”分离方法。已先读此前工业研究、四假设研究报告、combined 实测和本轮 small30 对比，避免将已有工程能力重新包装成新方法。

## 先纠正两个容易误导实现的认识

**DeepSeek 当前并非只有一种结构化输出能力。** 本地 `grounding/client.py` 使用 `/chat/completions` 与 `response_format: json_object`。官方 Chat 接口文档此字段只列 `text/json_object`，并将严格 tool calling 标为 Beta；强制指定 tool 在 thinking 模式不受支持。另一方面，当前官方 Responses 文档已列 `text.format.type=json_schema`，支持 `deepseek-flash`。这给出了独立能力探针的依据，尚未给出当前账户/代理链路/复杂 Schema 的实测保证。不要把 Chat JSON mode 叫作 schema enforcement，也不要未经探针就迁移整套客户端。[Chat API](https://api-docs.deepseek.com/api/create-chat-completion/) [Responses API](https://api-docs.deepseek.com/api/create-response/)

**格式成功、引用定位成功、语义成功是三件事。** DeepSeek JSON mode 仍公开列出空内容与截断边界；Google 明确要求应用继续验证字段值的语义。JSONSchemaBench 则同时研究生成效率、约束覆盖与任务质量，而非只数可解析 JSON。这些资料支持拆开测量，不支持“换成 Schema 就提高事实准确率”的推断。[DeepSeek JSON](https://api-docs.deepseek.com/guides/json_mode/) [Google Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output) [JSONSchemaBench](https://arxiv.org/abs/2501.10868)

## 代码与已有结果对研究的约束

当前 v4 已有安全引用归一化、错索引精确修正、内容差异候选重判、逐行保留成功输出、有界复核和阶段预算。建议“先 validator 再重问”若没有指出缺少哪一步，只是在重复已实现功能。`_batch()` 已保留其他合法行；不要为了局部格式缺陷整批重跑。

此前 combined 已实现 ID 证据回填、内部/公共证据分离、初判盲化与残留提取。它提高完整率但总体没有优化，且增加了更多提取目标、U 复核和 token。重新组合这四件事不能称作新的独立假设。small30 中 minimal 与 v4 的共同有效样本各正确 17/28；当前证据不足以认定必须维持九倍左右的调用数量才能达到相同语义质量。[组合实测](../../reports/v4-combined-20261023/README.md) [small30 对比](../../reports/ragtruth-small30-comparators-20261023/README.md)

下面仅保留三个可以小试的方向；它们都是本项目猜想，尚未证明收益。

## 方向一：Schema 能力探针与最小判决协议

**联合推导：** E02/E03 的接口差异 + E05/E06 的结构/语义分评 + E04 的位置回填，支持先降低“已知内容仍要求模型复制”的协议负担。不是再加一轮审查。

先做 12–16 个全新合成请求的能力探针：嵌套引号、反斜杠、Unicode、空数组、枚举、额外字段、S/C/U 分支、故意超小预算。比较同一任务说明下 Chat JSON mode 和 Responses JSON Schema；只检查预先声明支持的子集。HTTP 接受 schema 不等于真的约束生成；必须以本地独立验证器检查。故意截断用于确定错误行为，不能混进正常完成率作有利解释。

能力通过后，再将 **已知 claim_text 由代码按唯一 id 回填** 作为单因素实验；模型仍看到完整 claim，但不必逐字回显。保留必要推导和完整证据，不同时删解释、改 thinking、换 ID 引用和加路由。未知/重复/缺失 ID 一律失败；绑定需覆盖 request hash、claim id 与原始文本，避免串行/并发回填错配。若研究分支 Schema，U 的内部考察材料仍可保留，不能为了格式有效删掉真实语义诊断。

**主要反证：** 删除回显可能降低模型注意力；Schema 也可能约束错或增加冷编译时延；合法 ID 仍可选错；NF 漏检不由此解决。工程投入中等：独立 transport adapter、schema 能力声明、usage/finish 映射与回归测试。小试以有效率、已知字段复制错误、完整语义正确率、引文充分性、token/冷启动时延分开报告；不得只选解析率最高者。

## 方向二：薄层 single-call 对照，量化确定性修复的边际收益

**联合推导：** E07 的局部重试边界 + E08 的质量/预算联合目标 + E04 的准确定位职责分离，支持先比较一个有严格护栏的简单方案，再决定多阶段的必要性。

保留历史 `minimal` 完全不动，新实验名如 `single-call-guarded`。第一步仅在离线重放中对模型原始 JSON 使用现有安全 aligner；可证明内容不变的引用形态/唯一错索引修复后重新通过完整契约。数字、字母、实体、否定或有意义符号变化不能直修；模糊候选不自动替换。该步骤不新增模型调用，可直接测修复零误改不变量。

随后用全新合成变式做新鲜配对调用：固定事实密度、领域和表述族，原 single call 与仅增加确定性后处理的候选比较；必要时另设“只改 thinking”的独立轴，不与护栏收益混算。若候选升级为实际 v4 路线，还必须补齐 v4 的 M1 粒度、C conflict、U 复核与 partial 契约；仅恢复 minimal 完成度的诊断不能被标作合规 v4 替代。

**主要反证：** 原单次输出可能遗漏事实、把建议前提排除；完成率增加可能同时把错误输出恢复成完整报告。故必须统计完整且正确/全部输入、事实覆盖与 FP/FN；不声称 safe alignment 证明判决语义。投入低（离线重放）至中（新鲜配对+完整契约）。这项最适合快速确定“复杂度是否真的必要”，而非直接替换生产。

## 方向三：显式区分接口错误和语义缺口，用同预算复核测净收益

**联合推导：** E07 的重试预算 + E08 的有成本级联 + E10 的上下文位置偏差，支持在既有 C/U 资格和次数内，按**确定性可观察缺陷**传入足够局部诊断，并保留全原文回查。它不支持用未经校准的 LLM confidence 跳过规定复核。

先冻结同一批初判与触发集合，比较当前修复信息与精简结构化缺陷记录；总调用次数相同，全部保留原文。诊断只写缺字段、非法索引、非精确引文等可证明事实；不能夹带预期标签。已有位置/ID、原文数字/符号保持原样。最终用错→对、对→错、未变、报错及 token/成本衡量，净翻转不是净修正。若现有 terse/detailed repair 探针已经没有收益，应降低优先级，不重复寻找措辞直到得高分。

**主要反证：** 结构诊断更短不一定语义更好；已有前次修复诊断探针不支持冗长说明收益，因此该方向优先级低于前两项。缓存布局只能是附带成本检查：当前 `_batch` 已将共享 context 放在 claims 前，先测 prefix/usage，再决定是否改变排列；不要为了缓存裁掉证据或让所有请求等预热。跨供应商缓存行为也不能从 DeepSeek 文档外推。

## 小实验的统一约束

- 一次只隔离一个变化；先代码/Prompt/模型/预算冻结，再执行。不给实验后端 benchmark 名称、ID、金标或生成器信息。
- 合成集合从通用契约造：不同实体、领域、句法、语言、来源顺序；既含应修复的格式变式，也含不得直修的内容变式。不从已知败例抄文本或模板。
- 一旦用于选方案，集合即开发集；失败保留，不换样本补跑。现有 30 条可以作为已曝光回归，不能叫新确认。
- 对每个变化报完整/partial/error、有效 claim 覆盖、完整且正确/总数、语义对→错、全部调用 token、缓存实际与全未命中参考成本。事前固定很小的调用上限；24/48 次调用可筛掉显著工程失败，不能证明泛化提升。
- 所有建议保持 `3.5≠35`、`−5≠5`，字母/数字绝不归一化折叠；内容差异需要重新判决。M1 独占粒度，不引入运行时合并。

**本子任务结论：** 优先研究更小、可验证的输出协议和薄层护栏对照；严格 Schema 是值得先探测的工程能力，当前没有证据将其作为语义修复。用缺陷类型做有界恢复已有大部分实现，真正新增价值必须通过独立消融呈现。
