# Gemini High 结果审阅：采纳与纠正

`gemini-4-argon-high`、`effort=high`，通过无界面 Antigravity CLI 完成；`validation.json` 确认 SUCCESS、没有工具调用步骤或 stderr。它看到的是本轮已经独立复算的汇总资料，未自行运行测试或检查原始数据。原始答复保存在 `gemini-results/response.md`，保持不改写。

## 采纳

- 全 180 条正确判定净增 15 条，来源簇主指标区间在零以上；条件 F1 区间跨零，不能称所有指标稳定胜出。
- 误报仍高；阴性占多数，不能将 57.22% 的绝对准确率包装为高水平。改善集中于 QA 的观察只作为描述，不作为针对本 benchmark 特调的依据。
- 费用缺两次 usage，必须保持总额未知；缓存口径和全未缓存口径分开。调用数、翻转数和完成率不等于模块纠错收益或事实召回。
- 当前实验是非等预算、非等并发的系统比较，不支持单一模块的因果归因。后续问题须在新的独立数据与预先冻结的协议中检验。

## 明确纠正：它把案例级时延误读成了子调用时延

原答复第 3.1 节说 18.41 秒是 1,434 次子调用的均值，因此不能比较案例端到端时延；第 4.4 节建议补齐案例级时延。**这两处不正确，不采纳。**

冻结 `run.py::infer_one` 在调用完整 `instance.verify(request)` 前开始 `time.monotonic()` 计时，成功或失败后写入每条回答×后端结果的 `latency_seconds`（冻结文件约第 249–285 行）。`summarize.py::runtime` 从每个 backend 的 **180 条案例记录**读取这一字段，直接计算 mean/P50/P95（约第 63–71 行），没有从 `telemetry.calls` 计算该时延。独立审计也复算了这些值。

因此，18.413 秒与 32.207 秒确实是两套系统各自完整 verify 调用的案例级墙钟均值，包含拆分、内部修复、核查、重问和复核。可以陈述“在本轮配置与调度下，v4.0 案例级实测更快”，但不能据此证明相同预算/并发下算法本身更快；也不包含 HTTP 网络/服务排队或外层案例排队时间。

## 其他措辞限制

- “全阳基线”只能指 baseline 在这批数据上全部报阳的**观测行为**，不能改写成它被实现为常量阳性分类器。
- `decompose_repair` 136 次 / `decompose` 195 次是调用计数比，不直接等于唯一块的首次失败率；报告保留原始事件数。
- minimal 的 FN=0 以三个原生阳性未决为条件。不能通过它与 v4.0 的 FN=2 推导 U 复核引入了这两个漏检；缺少固定 claims 与受控复核比较。
- bootstrap 区间由本地冻结评分与独立脚本计算。Gemini 仅审核提供的数字，不能把其“全部统计逻辑无误”写成第三方重新运行 bootstrap 的证据。

本次讨论的 usage 为 input 9,127、output 6,771（含 thinking 4,891）、total 15,898，按工具原字段记录；与被测 DeepSeek 三方案计量完全分开。计划审阅的独立 usage 见 `gemini-plan/final-result.json`。
